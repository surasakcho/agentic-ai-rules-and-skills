# Planning a sprint

**A sprint is a GOAL with a committed list. It ends when the list is done or when it is declared
failed. It never ends on a date.**

## Shape

One goal, stated as an outcome someone outside the team could recognise. *"The venue can be shown to
a stranger"*, not *"do the security work"*.

**Three to six committed items.** More than six is a backlog with a title on it.

## Before committing an item, all four must hold

1. **It has a PRD**, or it is a fix to an already-reproduced defect, or it is not code at all.
2. **It touches a screen? Then a mockup is committed with it**, as its own item, before the build.
3. **Its owner is named** — and if the owner is the shareholder, say so out loud, because that item
   can block the whole sprint while nobody is working on it.
4. **It is in `docs/kanban.md`.** Nowhere else.

## ⭐ Name the abandon condition when you open the sprint, not when it hurts

**Write down what would make you abandon this goal rather than push harder.** A sprint with no
abandon condition cannot fail, and a thing that cannot fail cannot inform anything.

## The one question that decides whether the sprint is real

**Name the artifact that ships when this sprint succeeds.** If the honest answer is a document, a
measurement or a decision, the sprint is not an engineering sprint — say so and plan it as what it
is, rather than discovering at the end that nothing was ever going to ship.

## Getting it approved

Propose the goal and the list. **Get approval once, at the start, then run without interrupting.**
Blocked items owned by the shareholder go on the tracker as questions, not into a chat message.
