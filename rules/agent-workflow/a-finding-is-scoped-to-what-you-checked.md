# A finding is scoped to what you actually checked — never to what it sounds like it means

**Task type:** agent workflow — any finding derived from one case and then applied to others.
**Related:** [`known-blast-radius-demands-scoped-fix-everywhere`](known-blast-radius-demands-scoped-fix-everywhere.md)
governs a set that is *"known precisely — not estimated, enumerated"*; **this rule is what happens
when you skip the enumeration and act on the estimate.**
[`read-the-manual-first`](read-the-manual-first.md) is the obligation to find the record;
this is the obligation to keep going back to it after you have summarised it.

---

## The rule

**When a finding from one case is about to be applied to a second case, open the second case and
check that the finding's premise actually holds there. Do not carry it across on the strength of
what it sounds like it means.**

And the harder half:

**Your own summary of the record is not the record.** A summary is a lossy index. It was accurate
about the case that produced it, and it is silent — not negative, *silent* — about every case it
did not look at. Acting on the index instead of the source is invisible from the inside, because a
summary you wrote yourself feels like knowledge rather than like a claim.

## The two shapes this takes

**1. "X was missing from the model I checked" becomes "X is missing from every model."**
The first is a finding. The second is a guess wearing the first one's authority. Applying it
without opening the other models produces a **double-count** where the item was already there —
and a correction published on that basis has to be retracted, which costs more than the original
omission.

**2. "The record says we can't do this" becomes an approach you propose anyway.**
Not because the record was never read, but because it was read, compressed, and the compression
dropped the specific prohibition. The tell is proposing something the log already rejected, in a
file you have edited recently.

## Why the estimate feels like an enumeration

Because both come out as a *sentence*. "Every model omits X" and "the four models I opened omit X"
read identically once written down, and only one of them is a finding. The number of cases checked
does not survive the summarisation, so it cannot be recovered later by re-reading your own note —
only by going back to the sources.

**This is why the count belongs in the sentence.** "Absent from the model I checked" and "absent
from all four models" are both cheap to write and impossible to confuse. "Absent from every model"
is the phrasing to distrust.

## What to do instead

| | |
|---|---|
| **Before applying a finding to case N+1** | Open case N+1. Confirm the premise holds there specifically. This is usually seconds of work |
| **When writing the finding down** | Record **how many cases you checked and which ones** — inside the claim, not in a footnote |
| **When a claim starts with "every", "all", or "none"** | Treat it as a flag. Either enumerate, or narrow the wording to what was checked |
| **Before proposing an approach** | Re-open the record — especially if you already summarised it, and *most* especially if you wrote that summary recently enough to feel confident about it |
| **After a retraction** | Ask which *other* claims rest on the same un-enumerated generalisation. There is usually more than one |

## The incident

One session produced both shapes within hours of each other.

A verified finding — a cost line was missing from one component's financial model — was written up
as *"absent from every model"* and applied to a second component. **That second model already
carried the cost, at a higher rate than the verified one.** The correction had already been
reported before anyone opened the second model. It became a double-count, a retraction, and a
correction to a correction.

Later the same day, the same session designed an experiment on a specific platform. The project's
own log already carried, from primary research: *do not run this experiment on this platform; a
null result there is uninterpretable.* The session had **edited that very file hours earlier.** It
had read the log, formed a summary, and then acted on the summary — which had kept the platform's
name as a candidate and dropped the ruling against it.

**Neither failure was a failure to look. Both were failures to look *again*, after summarising.**

## Guard

Before a finding crosses from one case to another, answer in one line: **which cases did I open, and
is this one of them?** If the answer is "I opened one and this is a different one", the finding has
not been established here yet — and saying so costs a sentence, where being wrong costs a retraction.
