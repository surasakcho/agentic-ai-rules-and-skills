# Nothing leaves git without the user's say-so

**Task type:** agent workflow — any moment you are about to write `.gitignore`, stage
selectively, or run a generator over a file that already exists.
**Related:** [`surgical-verified-change`](../coding/surgical-verified-change.md) is about keeping
a change small; this is about not making an unrequested one at all.
[`scratch-code-lives-outside-the-repo`](../coding/scratch-code-lives-outside-the-repo.md) decides
what should never enter the repo — this decides what may never *leave* it.

---

## The rule

**You may not exclude a file from version control on your own judgement. Ask, every time.**

That covers `.gitignore` patterns, selective `git add`, `git rm --cached`,
`--assume-unchanged`, and `--skip-worktree`. It covers proposing a `.gitignore` for a new
repo: propose the list, do not apply it.

And the corollary that gives it teeth:

**An untracked file has no undo. If it is not in git, every overwrite is permanent.**

## "It's only build output" is not a reason

It is the most common reason given, and it was the reason in the incident below. It is wrong
because *generated* and *disposable* are different properties, and only the user knows which
applies:

- A generated file gets opened in a GUI and hand-edited, and is now the only copy of that work.
- A generated file takes forty minutes and an API budget to rebuild.
- A generated file is the artifact actually being shipped; the generator is scaffolding.

You cannot see any of this from the file. The user can. **Classification is theirs.**

## Before overwriting anything that already exists

Any generator, build script, formatter, or codegen run that writes over an existing file:

- **Check the mtime.** Newer than your last run means something else wrote it.
- **Check the content.** A header, a build stamp, a size that does not match what your
  generator emits — in the incident, a 294 KB file where the generator produces 76 KB, and
  the size was visible in a directory listing that had already been read.
- **Copy it aside first** when there is any doubt, and say that you did.

## "Study it" means read only

When asked to *study*, *learn from*, *look at*, or *investigate* a file: read, then report.
Do not port the finding into other files, refresh examples, or rebuild anything. Extra
unrequested work is not a bonus — it is the mechanism by which the user's work gets destroyed.
Ask before changing any file.

## Why this matters more than it looks

Every other kind of agent mistake is recoverable. A wrong edit to a tracked file is
`git checkout`. A bad commit is `git revert`. A wrong answer is a follow-up question.

Deleting an untracked file is the one action with **no undo inside the repo at all**. Recovery
depends entirely on something outside git — a filesystem snapshot, OneDrive version history, a
backup that may not exist. That asymmetry is the whole reason this rule is absolute rather than
a judgement call: the downside is unbounded and the cost of asking is one sentence.

## The incident

*2026-08-19, a Tableau workbook deck built by hand-authoring XML.*

`compendium.twb` was generated by `build_compendium.py` from six per-figure source workbooks,
so it had been gitignored as build output — a decision the agent made and the user never
reviewed. The user then opened it in the Tableau GUI, solved a problem that had been open for
days (matching data-label colour to line colour), dragged four labels into place, and saved.

The user's next instruction was: **"I just found a way to match label to line color in fig 5.
learn from the file and update API doc."**

The agent read the file, found `color-mode='match'`, and then — unasked — edited the figure
source, overwrote an example workbook in a second repo, and re-ran `build_compendium.py` to
"verify". That run regenerated `compendium.twb` and destroyed the user's save.

Four failures, each of which alone would have prevented it:

1. **The exclusion was never the agent's to make.** Gitignoring the file removed the only
   undo that would have made the rest recoverable.
2. **"Learn from the file and update the doc" was read as licence to edit.** Only the doc
   update was requested.
3. **The build ran without copying the target aside**, over a file whose mtime was two hours
   newer than every source it was built from.
4. **The evidence was already on screen and went unread.** A directory listing four tool calls
   earlier showed `compendium.twb` at 294,325 bytes against a generator that emits ~76 KB.

What survived was luck: the agent had grepped the file for label markup before the overwrite,
so `color-mode='match'` and three of four label positions were recoverable from the tool
transcript. The rest of the session's GUI edits were only recovered because the folder happened
to sit in OneDrive and version history still held the 9:32 PM save. Neither of those is a
recovery strategy.

The user's instruction afterwards, which is now this rule:

> "before excluding any file from git commit, ask for my decision first. never decide on your own."
